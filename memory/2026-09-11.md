## ⚠️ iMessage delivery lesson — `imsg send` HANGS, use `send-rich`

Burned several minutes on this. Documented in TOOLS.md.

1. `message` tool was NOT in my policy-filtered toolset this run. Fell back to
   the `imsg` CLI per TOOLS.md.
2. `imsg send --chat-id +14438571551` → **fails**, "Unknown chat id". The
   `--chat-id` flag wants the *numeric* chat id, not a phone number.
   Get it from `imsg chats`. Chris = chat id **2**.
3. `imsg send --chat-id 2 --text ...` → **hangs indefinitely**, gets SIGKILLed.
   This is the known AppleScript-path hang. Message does NOT deliver.
4. ✅ **What worked:** `imsg send-rich --chat 'iMessage;-;+14438571551' --text ...`
   → "send-rich: queued", exit 0, delivered in <8s.
   Get the guid via `imsg group --chat-id <id>`.

**Always verify delivery with `imsg history --chat-id <id> --limit 1`** —
do not trust a hung/killed send. I nearly reported success on a message that
never sent.

## 🎯 Found the exact EACCES landmine before it fired

Audited file permissions across `api/` + `frontend/public/` (the deploy payload):
```
 42 files  -rw-r--r--  (644, fine)
  1 file   -rw-------  (600) ← api/shared/f1.js
 17 dirs   drwxr-xr-x  (755, fine)
```

**`api/shared/f1.js` is mode 600.** That is the NEW file created for the Results-display
fix — the shared F1 grid/tie-splitting module imported by BOTH `score-week.js` and
`api/standings`. It is exactly the kind of file that caused the historical
"EACCES: permission denied → whole API returns 500" outage that motivated moving
deploys to GitHub Actions.

So if anyone runs a local `swa deploy` right now **without** the chmod step, it would
ship a 600 file into the Linux Functions worker and **break the entire API** — during
Week 1, with 11 players and live picks.

**Mitigation is one command** (the same normalisation the workflow does):
```
find api -type d -exec chmod 755 {} + ; find api -type f -exec chmod 644 {} +
find frontend/public -type d -exec chmod 755 {} + ; find frontend/public -type f -exec chmod 644 {} +
```

**This materially changes the deploy-path advice:** a local `swa deploy` is safe *provided*
perms are normalised first. `swa` CLI 2.0.8 is installed. I have NOT run it — deploying is
Chris's call under the freeze — but the risk is now identified and one command from being
neutralised rather than being an unknown hazard.
