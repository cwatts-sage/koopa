**The actual gap:** `ACS_CONNECTION_STRING` was never set in the SWA app settings.
So `isConfigured()` returned false → every reset silently saved a token and skipped
the send. Classic silent no-op.

**Fix (two steps, and step 2 is the one I missed first):**
1. `az staticwebapp appsettings set --name watts-football-pool --resource-group NFL \
   --setting-names "ACS_CONNECTION_STRING=$(cat ~/.openclaw/secrets/acs-nfl-cs.txt)"`
2. ⚠️ **MUST force a Functions host restart** — SWA does NOT hot-reload app settings
   into a running host. Bump `WFP_RESTART=$(date +%s)` as a setting. Chris's 16:28
   click failed for exactly this reason; the 16:32 one (post-restart) worked.

### 🔑 LESSONS (I called this "fixed" twice and was wrong twice)
- **Setting an SWA app setting ≠ the app seeing it.** Always bump WFP_RESTART after,
  then re-verify. Don't declare done on the `az` exit code.
- **Response latency is NOT proof of delivery.** I read a 2.86s response as "email
  sent" — it only proved a send was *attempted*. Real bar = message in the inbox.
- Useful timing tell on /api/forgot-password: ~0.2-0.4s = no send (unknown user or
  60s cooldown); ~2.5-3s = real ACS handoff. Good signal, NOT proof.
- **Verify with the user before claiming success.** Two false "it's live" calls hurt
  trust more than the extra 60s of checking would have cost.

### Gotchas worth keeping
- Route is **`/api/forgot-password`** (kebab, from function.json `route`), NOT
  `/api/forgotPassword`. My first probe 404'd on this.
- App Insights telemetry is STALE/not ingesting (last data 16:00Z). Couldn't read
  Function logs at all. Debug via Table Storage state + ACS poller status instead.
- `az monitor app-insights query` wants the **component name** (`watts-football-pool`),
  not the appId GUID.
- To get terminal ACS delivery status: `beginSend()` then `await poller.pollUntilDone()`
  → `{id, status:"Succeeded", error:null}`. This is the real receipt.
- Sender is `DoNotReply@90f2aef4-...azurecomm.net` (Azure-managed). Custom domain
  wattsupcloudsolutions.com still CANNOT be used (MultipleSPFRecordsFound; required
  SPF would break Chris's iCloud mail). Delivery to @me.com/@icloud.com works fine
  from the managed domain — my "Apple is filtering us" theory was WRONG.
- users table: rowKey IS the email; `email` attribute is null. Don't look for it.
